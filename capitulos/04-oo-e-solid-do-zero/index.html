Antes da aula · ponto de partida

A biblioteca da Dona Marta [01]

A história de hoje

A Dona Marta cuida da biblioteca do bairro. Um sobrinho fez um programa em Java para o balcão: empresta livros, recebe devoluções e cobra multa por atraso. Funciona. Até que, numa segunda-feira, a Ana e o Bruno aparecem com o mesmo exemplar de Dom Casmurro anotado no nome dos dois. Na sexta, a coordenação pede para mudar o valor da multa, e o sobrinho, mexendo nesse cálculo, quebra sem querer o envio dos avisos.

Nenhum desses problemas é falta de Java. O programa compila, os testes passam. O problema é onde as regras moram. Hoje elas estão espalhadas, e qualquer parte do código pode mexer em qualquer coisa.

A frase do dia: uma mudança, um lugar. Cada regra deveria morar em um lugar só, perto do dado que ela protege. Assim, quando algo muda, você mexe ali e mais nada quebra.

Tudo o que veremos hoje, de objeto e encapsulamento até as cinco letras do SOLID, é um jeito diferente de cumprir essa frase. Guarde-a. Ela volta no fim.

Hoje o projeto é novo e independente

Não usamos nada dos capítulos anteriores. O ponto de partida é um projeto Java pequeno: cinco classes, cinco testes, sem Spring, sem Docker e sem banco de dados. Cada passo da prática tem um ZIP de retomada. Se você travar, baixa o do passo anterior e segue com a turma.

Classe é a ficha em branco. Objeto é a ficha preenchida. [03]

Uma ficha, muitos livros

Na biblioteca da Dona Marta há uma gaveta de fichas em branco, todas iguais, com os campos código, título e disponível. Cada livro do acervo ganha uma ficha preenchida: a de Dom Casmurro, a de Iracema, a de O Cortiço.

Em Java, a ficha em branco é a classe: ela descreve quais informações um livro tem. Cada ficha preenchida é um objeto (também chamado de instância): um livro de verdade, com os próprios valores. Quem cria um objeto a partir da classe é a palavra new.

Repare: a classe não tem título nenhum. Ela só diz que todo livro terá um título. Quem tem título é cada objeto.

Livro.java · como está no projeto hojea ficha em branco
public class Livro {

    public String codigo;
    public String titulo;
    public boolean disponivel = true;
}
criando dois objetosduas fichas preenchidas
Livro a = new Livro();      // uma ficha nova, em branco
a.titulo = "Dom Casmurro";    // preenchendo a ficha

Livro b = new Livro();      // outra ficha, independente da primeira
b.titulo = "Iracema";

Os valores guardados num objeto (o título, se está disponível) formam o seu estado. Dois objetos da mesma classe têm estados independentes: emprestar Dom Casmurro não muda nada em Iracema. O simulador mostra isso.

A variável guarda o caminho até a ficha

Um detalhe que confunde muita gente: a variável a não é o objeto. Ela guarda uma referência, algo como o endereço da ficha na gaveta. Se você escreve Livro c = a;, não nasce uma ficha nova: c e a passam a apontar para a mesma ficha. Só new cria objeto.

Preveja: o que este código imprime?

três variáveis, quantos livros?
Livro a = new Livro();
a.titulo = "Dom Casmurro";
Livro c = a;
c.titulo = "Iracema";
System.out.println(a.titulo);

Escolha uma previsão. Depois confira a explicação.

⚠️ Limite da analogia

A ficha de papel é só uma imagem. Na memória do computador, o objeto é um bloco de dados criado pela JVM (a máquina virtual que roda o Java), e ele some sozinho quando ninguém mais aponta para ele. Isso é a coleta de lixo, e você não precisa cuidar disso hoje.

Parte 1 · dados e regras juntos 13:55 · 10 min

O que o objeto sabe e o que ele faz [04]

Atributos e métodos

Uma classe tem dois tipos de coisa. Os atributos (ou campos) são o que o objeto sabe: código, título, se está disponível. Os métodos são o que o objeto faz: emprestar, devolver, dizer se está disponível.

No nosso Livro de hoje só existem atributos. Ele é um saquinho de dados. Quem decide o que acontece com ele é outra classe, a Biblioteca:

Biblioteca.java · como está hojea regra mora longe do dado
public void emprestar(Livro livro) {
    livro.disponivel = false;   // ninguém pergunta se ele já estava emprestado
}

A regra "um livro emprestado não pode ser emprestado de novo" não está escrita em lugar nenhum. E, se alguém a escrevesse aqui, qualquer outra parte do programa que fizesse livro.disponivel = false pularia a regra. Foi assim que a Ana e o Bruno ficaram com o mesmo livro.

A ideia central da orientação a objetos

Orientação a objetos (OO) é organizar o programa em objetos que juntam dados e as regras sobre esses dados. Em vez de um "chefe" que mexe em todos os saquinhos, cada objeto sabe cuidar de si. O livro sabe se pode ser emprestado. O balcão só pede: "livro, empreste-se".

É por isso que este capítulo se chama "OO de verdade": dá para escrever Java com classes o dia todo sem nunca fazer orientação a objetos, se todas as classes forem saquinhos de dados. O nome técnico desse jeito é modelo anêmico, objetos sem comportamento.

Saquinho de dados

O Livro só guarda valores.

A regra vive em quem usa (a Biblioteca, uma tela, um relatório…).

Cada lugar novo que usa o livro precisa lembrar da regra.

Objeto de verdade

O Livro guarda valores e tem emprestar().

A regra vive dentro do próprio livro.

Quem usa só chama o método; esquecer a regra fica impossível.

Onde deve morar a regra “não emprestar livro já emprestado”?

Encapsulamento: o objeto se protege [05]

Fechar a porta e deixar um guarda

Ter o método emprestar() não basta se o campo continuar aberto: alguém ainda pode escrever livro.disponivel = true e passar por fora. Precisamos de duas coisas juntas:

  1. Fechar a porta: o campo vira private. Só o código de dentro da própria classe Livro consegue ler ou mudar esse campo. De fora, o compilador recusa.
  2. Deixar um guarda: um método public que é o único caminho para mudar o estado, e que confere a regra antes. Se a regra não deixa, ele recusa com uma exceção (um sinal de erro que interrompe a operação).

Esse par, dados escondidos mais comportamento que guarda as regras, se chama encapsulamento. A palavra vem de "cápsula": o que está dentro fica protegido do lado de fora.

Livro.java · encapsulado (é o que faremos no passo 1)a regra mora no livro
public class Livro {

    private final String codigo;
    private final String titulo;
    private boolean disponivel = true;

    public Livro(String codigo, String titulo) {   // construtor: só nasce livro com código e título
        this.codigo = codigo;
        this.titulo = titulo;
    }

    public void emprestar() {
        if (!disponivel) {
            throw new IllegalStateException("O livro " + titulo + " já está emprestado.");
        }
        disponivel = false;
    }

    public boolean estaDisponivel() {
        return disponivel;
    }
}

private: de fora da classe, ninguém lê nem escreve disponivel. Tentar dá erro de compilação, antes mesmo de rodar.

final: código e título recebem valor uma vez, no construtor, e nunca mais mudam.

Construtor: o método especial com o nome da classe, chamado pelo new. Ele garante que todo livro nasce completo: new Livro("L-001", "Dom Casmurro").

throw new IllegalStateException(...): lança uma exceção que diz "o objeto não está num estado que permita isso". A operação para ali, e o livro continua como estava.

Parte 1 · a confusão mais comum 14:25 · 10 min

Getter e setter não são encapsulamento [06]

A porta fechada com a chave pendurada do lado de fora

Muita gente aprende a deixar o campo private e logo criar dois métodos para ele: o getter (getDisponivel(), que devolve o valor) e o setter (setDisponivel(boolean), que troca o valor). Muitas IDEs geram os dois com um clique.

O getter costuma ser inofensivo: ele só deixa ler. O setter genérico é o problema. setDisponivel(true) faz exatamente o que disponivel = true fazia: deixa qualquer um mudar o estado sem passar pela regra. A porta está fechada, mas a chave está pendurada do lado de fora.

A pergunta que separa um do outro é: esse método fala a língua do negócio? Na biblioteca, ninguém "seta disponível". Livros são emprestados e devolvidos. Métodos com esses nomes podem conferir regras; um setter não sabe o que está acontecendo.

Parece encapsulado

private boolean disponivel;

public void setDisponivel(boolean d) {
    disponivel = d;
}

Qualquer código faz setDisponivel(false) duas vezes e ninguém reclama.

É encapsulado

private boolean disponivel = true;

public void emprestar() { ... }
public void devolver() { ... }
public boolean estaDisponivel() { ... }

Só existem os caminhos que o negócio conhece, e cada um confere a sua regra.

O agente entregou esta versão do Leitor. O que você diz na revisão?

Leitor.java · proposta do agente
private String nome;
private String email;
private String tipo;

public String getTipo() { return tipo; }
public void setTipo(String tipo) { this.tipo = tipo; }
// ... getters e setters para todos os campos

Escolha a sua revisão.

⚠️ Quando um setter é aceitável

Em classes que só transportam dados de um lado para o outro (um formulário, um JSON que chega pela rede), getters e setters são comuns e não fazem mal: não há regra para proteger. O alerta vale para objetos que têm regras, como o Livro.

Interface: um contrato, vários jeitos de cumprir [07]

A tomada da parede

A tomada da sua casa não sabe se você vai ligar uma geladeira, um carregador ou um abajur. Ela só define um formato: dois ou três pinos, numa certa voltagem. Qualquer aparelho que respeite o formato funciona ali. Você troca o aparelho sem trocar a parede.

Em Java, esse formato é uma interface: uma lista de métodos que uma classe promete ter, sem dizer como. Uma classe que cumpre a promessa escreve implements e dá o corpo de cada método. A interface é o contrato; cada classe é um jeito de cumprir.

o contrato e dois jeitos de cumprirusaremos no passo 3
public interface TipoDeLeitor {
    int multaPorDiaEmCentavos();      // a promessa: sem corpo
}

public class Aluno implements TipoDeLeitor {
    @Override
    public int multaPorDiaEmCentavos() { return 100; }   // R$ 1,00
}

public class Professor implements TipoDeLeitor {
    @Override
    public int multaPorDiaEmCentavos() { return 50; }    // R$ 0,50
}

interface: só a lista de métodos. Não dá para fazer new TipoDeLeitor(); ela não é um objeto, é um formato.

implements TipoDeLeitor: “eu cumpro esse contrato”. Se a classe esquecer um método, não compila.

@Override: uma anotação que avisa “este método vem do contrato”. Se você errar o nome, o compilador reclama.

Valores de dinheiro em centavos e inteiros (100 = R$ 1,00), para não sofrer com arredondamento de números quebrados.

Polimorfismo: a mesma chamada, respostas diferentes

Agora o código que calcula a multa pode ser uma linha só, e ele não sabe se está falando com um aluno ou com um professor:

int multa = diasDeAtraso * leitor.getTipo().multaPorDiaEmCentavos();

Cada objeto responde do seu jeito. Esse efeito tem nome: polimorfismo (do grego, “muitas formas”). O código que chama fica igual; o comportamento muda conforme o objeto que está do outro lado da tomada.

Repare também que o Leitor agora tem um TipoDeLeitor guardado num campo. Montar objetos com outros objetos dentro se chama composição. É diferente de herança (extends), que diz “é um tipo de”. Herança aparece no ponto 15, com um cuidado importante.

⚠️ Primeira seta do dia: () ->

Nos testes novos o agente vai escrever assertThrows(IllegalStateException.class, () -> biblioteca.emprestar(livro));. O trecho () -> ... é uma lambda: um pedaço de código entregue para o teste rodar e verificar se ele lança a exceção. Hoje basta reconhecê-la.

Na sua IDE essa seta pode aparecer desenhada como →, por causa de um recurso da fonte chamado ligatura. Se for digitar, são dois caracteres: - (hífen) seguido de > (maior que). Se você digitar o símbolo →, o Java não compila.

SOLID: cinco conselhos, não cinco leis [10]

De onde vem

SOLID é um acrônimo: cada letra é a inicial de um princípio de design de classes. Os princípios foram reunidos por Robert C. Martin no começo dos anos 2000, e a sigla foi sugerida por Michael Feathers. Em inglês, solid quer dizer “sólido”: código que aguenta mudanças sem desmoronar.

São conselhos, não leis. Cada um responde a uma dor concreta. Se a dor não existe no seu código, aplicar o conselho só acrescenta arquivos. Hoje, cada letra começa pela dor e termina com o limite.

LetraNome (inglês → português)Em uma frase
SSingle Responsibility → Responsabilidade ÚnicaUma classe deve ter um só motivo para mudar.
OOpen/Closed → Aberto/FechadoDá para acrescentar comportamento novo sem editar o que já funciona.
LLiskov Substitution → Substituição de LiskovUm filho deve cumprir as promessas do pai.
IInterface Segregation → Segregação de InterfacesNinguém deve ser obrigado a prometer o que não faz.
DDependency Inversion → Inversão de DependênciaDependa do contrato, não do detalhe.

Repare que as cinco frases são variações da frase do dia. Cada conselho, à sua maneira, tenta fazer uma mudança cair em um lugar só.

S · Responsabilidade Única: um motivo para mudar [11]

A dor: mexer na multa e quebrar o aviso

Lembra da sexta-feira? A coordenação pediu para mudar o valor da multa, o sobrinho mexeu em Biblioteca.devolver() e quebrou o envio do e-mail, que estava no mesmo método, poucas linhas abaixo. Ninguém pediu mudança no e-mail. Ele quebrou porque morava junto.

O conselho S diz: uma classe deve ter um só motivo para mudar. “Motivo” aqui quer dizer quem pede a mudança. Na biblioteca há três fontes de pedido diferentes:

  • a coordenação, que decide quanto custa o atraso;
  • a TI, que decide como o aviso chega (e-mail, WhatsApp);
  • o balcão, que decide as regras de empréstimo (essa já foi para o Livro no passo 1).

Uma classe que atende três pessoas diferentes vai ser alterada por três motivos, em dias diferentes, por gente que não conversa. É aí que um conserto quebra outra coisa.

L · Substituição de Liskov: o filho cumpre a promessa do pai [15]

Primeiro, herança

Herança é quando uma classe diz “eu sou um tipo especial daquela outra”: class LivroInfantil extends Livro. A classe filha ganha tudo o que o pai tem e pode acrescentar coisas ou trocar o comportamento de um método (sobrescrever, com @Override). Onde o programa espera um Livro, ele aceita um LivroInfantil.

É essa última frase que importa. Se o programa aceita o filho no lugar do pai, o filho precisa se comportar como o pai prometeu. O conselho L, formulado por Barbara Liskov em 1987, diz exatamente isso: um objeto filho deve poder substituir o pai sem que quem usa perceba a troca.

A dor: o dicionário que não sai da sala

A biblioteca ganhou obras de consulta, como um dicionário que nunca pode ser emprestado. Alguém propõe o caminho rápido:

public class LivroDeConsulta extends Livro {
    @Override
    public void emprestar() {
        throw new UnsupportedOperationException("Obra de consulta não sai da biblioteca.");
    }
}

Compila. Mas o Livro prometia: “se eu estiver disponível, emprestar() funciona”. O filho quebra a promessa. Qualquer código que trabalha com uma lista de livros, como “emprestar todos os livros da lista de leitura para a turma”, explode no meio do caminho.

Aí o compilador impede colocá-la na lista de empréstimo. A regra prática: use herança só quando o filho for, de verdade, um caso do pai em tudo o que o pai promete. Na dúvida, prefira composição. I · Segregação de Interfaces: contratos pequenos [16]

A dor: prometer o que não faz

Imagine um contrato único para tudo o que existe no acervo:

public interface ItemDoAcervo {
    void emprestar();
    void devolver();
    String baixarPdf();
}

O livro de papel não tem PDF. O e-book de domínio público não se empresta: qualquer um baixa. Mas, para cumprir o contrato, cada classe é obrigada a escrever os três métodos, e os que ela não faz viram throw new UnsupportedOperationException(). É a mesma quebra de promessa do ponto 15, só que forçada pelo contrato.

O conselho I diz: ninguém deve ser obrigado a depender de métodos que não usa. Em vez de um contrato gordo, vários contratos pequenos: Emprestavel (emprestar, devolver) e Baixavel (baixarPdf). Cada classe assina só os que cumpre.

🧪 Simulador · o que cada classe é obrigada a escrever

⚠️ Limite do conselho

Também dá para exagerar: uma interface por método é ruído. Agrupe o que sempre anda junto (quem empresta sempre devolve) e separe o que varia de forma independente.

D · Inversão de Dependência: dependa do contrato, não do detalhe [17]

A dor: o e-mail soldado dentro do balcão

Olhe de novo a Biblioteca. Lá dentro há um new EmailSmtp(). Isso significa que a Biblioteca depende do EmailSmtp: não existe Biblioteca sem ele. Três consequências que você já sentiu ou vai sentir:

  • todo teste com multa espera os 2 s do e-mail falso;
  • o teste não tem como conferir se o aviso saiu, nem com que texto;
  • trocar e-mail por WhatsApp obriga a editar a Biblioteca, que não tem nada a ver com isso.

É como um abajur com o fio soldado na parede: para trocar a lâmpada, você chama o eletricista.

A saída: a tomada, de novo

O conselho D tem duas partes. Primeira: a regra de negócio (a Biblioteca) não deve depender do detalhe técnico (o EmailSmtp). Os dois devem depender de um contrato, a interface Notificador. Segunda: quem dita o contrato é quem precisa dele. A Biblioteca diz “eu preciso de alguém que saiba avisar um leitor”, e o e-mail se adapta a isso.

E quem escolhe qual notificador usar? Quem monta a Biblioteca: ela recebe o notificador pronto, pelo construtor. No programa de verdade (o App), quem monta passa o e-mail. No teste, passa um notificador falso que só anota. Receber as dependências pelo construtor, em vez de criá-las lá dentro, se chama injeção de dependência.

Glossário de bolso [23]

Classe
A descrição de um tipo de coisa: quais dados e quais comportamentos ela tem. A ficha em branco.
Objeto (instância)
Uma coisa concreta criada a partir de uma classe, com os próprios valores. A ficha preenchida.
new
A palavra que cria um objeto novo e chama o construtor.
Referência
O que uma variável de objeto guarda: o caminho até o objeto, não o objeto em si.
Atributo (campo)
Um dado guardado no objeto, como o título do livro.
Estado
O conjunto dos valores dos atributos de um objeto num dado momento.
Método
Algo que o objeto sabe fazer, como emprestar().
Construtor
Método especial com o nome da classe, chamado pelo new, que garante que o objeto nasça completo.
public / private
Quem pode usar: qualquer código / só o código da própria classe.
final
Num campo: recebe valor uma vez e nunca mais muda.
Encapsulamento
Esconder os dados e oferecer só métodos que conferem as regras.
Getter / setter
Métodos que leem / trocam um campo. O setter genérico pula as regras.
Modelo anêmico
Classes que só guardam dados, com as regras espalhadas em outro lugar.
Exceção
Sinal de erro que interrompe a operação. IllegalStateException: “o objeto não está num estado que permita isso”.
Interface
Um contrato: a lista de métodos que uma classe promete ter, sem o corpo.
implements
“Esta classe cumpre aquele contrato.”
@Override
Anotação que marca um método vindo do contrato ou do pai; o compilador confere o nome.
Polimorfismo
A mesma chamada produzindo comportamentos diferentes, conforme o objeto que responde.
Composição
Montar um objeto com outros objetos dentro (“tem um”).
Herança (extends)
Uma classe filha que é um tipo especial da classe pai (“é um”).
SOLID
Cinco conselhos de design de classes: S, O, L, I, D.
S · Responsabilidade Única
Uma classe, um motivo para mudar (uma fonte de pedidos de mudança).
O · Aberto/Fechado
Acrescentar comportamento com código novo, sem editar o que já funciona.
L · Substituição de Liskov
O filho cumpre tudo o que o pai promete; quem usa não percebe a troca.
I · Segregação de Interfaces
Contratos pequenos; ninguém promete o que não faz.
D · Inversão de Dependência
A regra de negócio depende de um contrato; o detalhe técnico se adapta a ele.
Injeção de dependência
Receber as peças prontas (pelo construtor) em vez de criá-las lá dentro.
Dublê de teste
Objeto que substitui o de verdade só no teste, como o NotificadorDeTeste.
Lambda
Um pedaço de código entregue como valor: () -> .... Digite hífen e maior que, nunca o símbolo →.
Maven Wrapper
O mvnw: baixa e roda a versão certa do Maven sem instalar nada.
JUnit
A biblioteca de testes do Java. @Test marca um teste; assertEquals confere um valor.
Diff
A lista do que mudou nos arquivos: linhas acrescentadas e removidas.
