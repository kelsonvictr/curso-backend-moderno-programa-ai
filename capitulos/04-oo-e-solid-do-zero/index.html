Antes da aula · ponto de partida

A biblioteca da Dona Marta [01]

A história de hoje

A Dona Marta cuida da biblioteca do bairro. Um sobrinho fez um programa em Java para o balcão: empresta livros, recebe devoluções, cobra multa por atraso e manda um aviso por e-mail. Funciona, e os testes passam. Mas cada pedido novo da Dona Marta vira um susto: visitantes passam a pegar livros e o programa cobra deles zero, sem reclamar. Chegam dicionários, que não podem sair da sala. Chegam e-books, que ninguém empresta: baixa. E os testes demoram, porque cada um espera um e-mail de mentira.

Nenhum desses sustos é falta de Java. O programa compila. O problema é onde cada regra mora e quem depende de quem. É disso que trata o SOLID: cinco conselhos para organizar classes de modo que um pedido novo não vire uma caça ao tesouro.

A frase do dia: uma mudança, um lugar. Cada pedido da Dona Marta deveria cair num lugar só do código. Você mexe ali, e mais nada quebra.

As cinco letras do SOLID são cinco jeitos de cumprir essa frase. Guarde-a: ela volta em cada ato e no fechamento.

Hoje o projeto é novo, e você escreve o código

Não usamos nada dos capítulos anteriores. O ponto de partida é um projeto Java pequeno: cinco classes e cinco testes. Hoje o código é digitado por você, não pelo agente: as mudanças são pequenas, e é digitando que você vê o compilador apontar cada lugar afetado. O agente aparece no fim, como revisor. Cada letra tem um ZIP de retomada.

De onde vem

Os princípios foram reunidos por Robert C. Martin no começo dos anos 2000; a sigla foi sugerida por Michael Feathers. Em inglês, solid quer dizer “sólido”: código que aguenta mudanças. São conselhos, não leis. Cada um responde a uma dor concreta; se a dor não existe, aplicar o conselho só acrescenta arquivos.

O mínimo de Java para hoje: classe, interface e herança [04]

Classe e objeto

Uma classe é a ficha em branco: diz que todo livro tem código, título e se está disponível. Cada objeto é uma ficha preenchida, criada com new: new Livro("L-001", "Dom Casmurro"). Os métodos são o que o objeto sabe fazer: livro.emprestar().

No nosso projeto, o Livro já se protege: o campo disponivel é private (ninguém de fora mexe nele) e o único caminho para emprestar é o método emprestar(), que recusa o segundo empréstimo. Esse cuidado se chama encapsulamento, e hoje ele já vem pronto.

Livro.java · o essencial (já vem no projeto)o livro cuida de si
public class Livro {

    private final String codigo;
    private final String titulo;
    private boolean disponivel = true;

    public void emprestar() {
        if (!disponivel) {
            throw new IllegalStateException("O livro " + titulo + " já está emprestado.");
        }
        disponivel = false;
    }
    // ... devolver(), estaDisponivel(), getCodigo(), getTitulo()
}

Interface: a tomada da parede

A tomada não sabe se você vai ligar uma geladeira ou um carregador. Ela só define um formato. Em Java, esse formato é uma interface: uma lista de métodos que uma classe promete ter, sem dizer como. A classe que cumpre escreve implements e dá o corpo de cada método. A interface é o contrato; cada classe é um jeito de cumprir.

um contrato e dois jeitos de cumprirvocê vai digitar isso no Ato O
public interface TipoDeLeitor {
    int multaPorDiaEmCentavos();      // a promessa: sem corpo
}

public class Aluno implements TipoDeLeitor {
    @Override
    public int multaPorDiaEmCentavos() { return 100; }   // R$ 1,00
}

public class Professor implements TipoDeLeitor {
    @Override
    public int multaPorDiaEmCentavos() { return 50; }    // R$ 0,50
}

implements TipoDeLeitor: “eu cumpro esse contrato”. Se a classe esquecer um método, não compila.

@Override: avisa “este método vem do contrato”. Se você errar o nome, o compilador reclama.

Dinheiro em centavos e inteiros (100 = R$ 1,00), para não sofrer com arredondamento.

Polimorfismo: a mesma chamada, respostas diferentes

Com o contrato, a conta da multa vira uma linha que não sabe se está falando com um aluno ou um professor. Cada objeto responde do seu jeito. Isso se chama polimorfismo (“muitas formas”).

🧪 Simulador · quem responde a chamada?

Escolha os dias de atraso e clique num leitor. Observe que a linha de cima nunca muda. Só muda quem responde.

Clique num leitor.

Herança: “é um tipo especial de”

A última peça: class LivroInfantil extends Livro diz que a classe filha é um tipo especial de Livro. Ela ganha tudo o que o pai tem e pode trocar um método com @Override. Onde o programa espera um Livro, ele aceita a filha. Guarde essa frase: ela é o centro da letra L.

S · Responsabilidade Única: um motivo para mudar [05]

A dor: três pessoas mexendo no mesmo arquivo

Na Biblioteca de hoje, o método devolver() faz três coisas: pede ao livro para voltar, calcula a multa e manda o aviso. Parece prático. O problema aparece quando alguém pede uma mudança.

O conselho S diz: uma classe deve ter um só motivo para mudar. “Motivo” quer dizer quem pede a mudança. Na biblioteca há três fontes de pedido diferentes:

  • a coordenação, que decide quanto custa o atraso;
  • a TI, que decide como o aviso chega (e-mail, WhatsApp);
  • o balcão, que decide as regras de empréstimo (essas já moram no Livro).

Uma classe que atende várias pessoas vai ser alterada por motivos diferentes, em dias diferentes, por gente que não conversa. É aí que um conserto quebra outra coisa: mexendo na multa, alguém apaga sem querer uma linha do aviso.

🧪 Simulador · para onde vai cada pedido de mudança?

Escolha a versão do código e clique nos três pedidos. Veja quais arquivos precisam ser abertos e quantas pessoas pedem mudança em cada um.

Clique num pedido de mudança.

Escolha uma resposta. Depois confira a explicação.

⚠️ Limite do conselho

“Um motivo” não é “um método por classe”. Separar demais espalha uma ideia por dez arquivos minúsculos, e entender o fluxo vira caça ao tesouro. A pergunta continua sendo: quem pediria essa mudança? Se é a mesma pessoa, pelo mesmo motivo, pode ficar junto.

O · Aberto/Fechado: crescer sem mexer no que funciona [06]

A dor: cada tipo novo abre o mesmo arquivo

A biblioteca vai atender visitantes, que pagam R$ 2,00 por dia. Com a multa escrita como if (tipo.equals("ALUNO")), o caminho óbvio é mais um if. Depois virão funcionários, parceiros… A cada tipo novo, alguém abre um arquivo que já funciona e já foi testado, e edita no meio dele.

Pior: enquanto ninguém lembra do if, o tipo novo cai no return 0 do fim e paga zero, em silêncio. Nenhum erro, nenhum aviso. O mesmo acontece se alguém digitar "ALUNOO".

O conselho O diz que o código deve ser aberto para extensão (dá para acrescentar comportamento) e fechado para modificação (sem editar o que funciona). Com o que você viu no ponto 04: um contrato (TipoDeLeitor) e uma classe nova para cada tipo.

🧪 Simulador · o que muda quando chega um tipo novo?

Escolha o jeito de escrever a multa e faça chegar tipos novos. Conte quantos arquivos que já existiam foram editados.

Faça chegar o Visitante.

Quando não vale a pena criar o contrato?

⚠️ Limite do conselho

“Fechado para modificação” não quer dizer “nunca mais mexa nesse arquivo”. Se a regra mudar (um teto de multa, por exemplo), você edita a calculadora, e tudo bem. O conselho fala de uma coisa só: acrescentar um caso novo não deveria exigir editar os casos que já existem.

L · Substituição de Liskov: o filho cumpre a promessa do pai [07]

A dor: o dicionário que não sai da sala

Lembra da herança do ponto 04? Onde o programa espera um Livro, ele aceita qualquer filha. Por isso a filha precisa se comportar como o pai prometeu. O conselho L, formulado por Barbara Liskov em 1987, diz: um objeto filho deve poder substituir o pai sem que quem usa perceba a troca.

A biblioteca ganhou um dicionário, que nunca pode ser emprestado. Alguém propõe o atalho:

o atalho que parece certocompila… e quebra a promessa
public class LivroDeConsulta extends Livro {
    @Override
    public void emprestar() {
        throw new UnsupportedOperationException("Obra de consulta não sai da biblioteca.");
    }
}

Compila. Mas o Livro prometia: “se eu estiver disponível, emprestar() funciona”. A filha quebra a promessa. Qualquer código que confia em Livro, como “emprestar todos os livros da lista da turma”, explode no meio do caminho.

🧪 Simulador · emprestar a lista da turma

A professora pede três livros para a turma. O código percorre a lista e chama emprestar() em cada um. Escolha o modelo e rode.

for (Livro livro : livros) {
    livro.emprestar();
}

Escolha um modelo e rode o laço.

Qual destas classes filhas respeita a promessa de Livro?

Escolha uma resposta. Depois confira a explicação.

⚠️ O que fazer, então?

Se a filha não consegue cumprir a promessa, ela não é um tipo especial do pai. A saída é não herdar: uma ObraDeConsulta separada, que nem tem emprestar(). Aí o próprio compilador impede colocá-la na lista de empréstimo. Use herança só quando a filha for, de verdade, um caso do pai em tudo o que o pai promete.

I · Segregação de Interfaces: contratos pequenos [08]

A dor: prometer o que não faz

Chegaram e-books de domínio público: estão no acervo e qualquer um baixa o PDF; ninguém empresta. Alguém propõe um contrato único para tudo o que existe no acervo:

um contrato para tudoo contrato gordo
public interface ItemDoAcervo {
    String getTitulo();
    void emprestar();
    void devolver();
    String baixarPdf();
}

O livro de papel não tem PDF. O dicionário não se empresta nem se baixa. O e-book não se empresta. Mas, para cumprir o contrato, cada classe é obrigada a escrever todos os métodos, e os que ela não faz viram throw new UnsupportedOperationException(). É a promessa quebrada do ponto 07, agora forçada pelo contrato.

O conselho I diz: ninguém deve ser obrigado a depender de métodos que não usa. Em vez de um contrato gordo, contratos pequenos: ItemDoAcervo só com o que todo item tem (código e título) e Baixavel só para o que se baixa. Cada classe assina os que cumpre.

🧪 Simulador · o que cada classe é obrigada a escrever

Escolha o contrato e a classe. Em vermelho, os métodos que só existem para lançar exceção.

⚠️ Limite do conselho

Também dá para exagerar: uma interface por método é ruído. Agrupe o que sempre anda junto (quem empresta sempre devolve) e separe o que varia de forma independente.

D · Inversão de Dependência: dependa do contrato, não do detalhe [09]

A dor: o e-mail soldado dentro do balcão

Dentro da Biblioteca há um new EmailSmtp(). Isso quer dizer que a Biblioteca depende do EmailSmtp: não existe uma sem a outra. Três consequências:

  • todo teste com multa espera os 2 s do e-mail de mentira;
  • o teste não tem como conferir se o aviso saiu, nem com que texto;
  • trocar e-mail por WhatsApp obriga a editar a Biblioteca, que não tem nada a ver com isso.

É como um abajur com o fio soldado na parede: para trocar a lâmpada, você chama o eletricista.

A saída: a tomada, de novo

O conselho D tem duas partes. Primeira: a regra de negócio (a Biblioteca) não deve depender do detalhe técnico (o EmailSmtp). Os dois dependem de um contrato, a interface Notificador. Segunda: quem dita o contrato é quem precisa dele. A Biblioteca diz “preciso de alguém que saiba avisar um leitor”, e o e-mail se adapta.

E quem escolhe o notificador? Quem monta a Biblioteca: ela recebe o notificador pronto, pelo construtor. No programa (o App), quem monta passa o e-mail. No teste, passa um notificador falso que só anota. Receber as peças pelo construtor, em vez de criá-las lá dentro, se chama injeção de dependência.

⚠️ Primeira seta do dia: () ->

O trecho () -> biblioteca.emprestar(livro) é uma lambda: um pedaço de código entregue ao teste, que o roda e confere se ele lança a exceção. Hoje basta reconhecê-la; você não vai precisar escrever uma.

Na sua IDE essa seta pode aparecer desenhada como →, por causa de um recurso da fonte chamado ligatura. Se for digitar, são dois caracteres: - (hífen) seguido de > (maior que). Se você digitar o símbolo →, o Java não compila.

  4. ✅ Rode o mesmo teste e compare com o começo do ato.

Glossário de bolso [21]

Classe / objeto
A ficha em branco / a ficha preenchida, criada com new.
Encapsulamento
Esconder o dado (private) e oferecer só métodos que conferem a regra, como emprestar().
Interface
Um contrato: a lista de métodos que uma classe promete ter, sem o corpo.
implements
“Esta classe cumpre aquele contrato.” Uma classe pode assinar vários, separados por vírgula.
@Override
Marca um método que vem do contrato ou do pai; o compilador confere o nome.
Polimorfismo
A mesma chamada produzindo comportamentos diferentes, conforme o objeto que responde.
Herança (extends)
Uma classe filha que é um tipo especial da classe pai (“é um”). super(...) chama o construtor do pai.
Composição
Montar um objeto com outros dentro (“tem um”): o Leitor tem um TipoDeLeitor.
SOLID
Cinco conselhos de design de classes: S, O, L, I, D.
S · Responsabilidade Única
Uma classe, um motivo para mudar (uma fonte de pedidos de mudança).
O · Aberto/Fechado
Acrescentar um caso novo com código novo, sem editar os casos que já funcionam.
L · Substituição de Liskov
A filha cumpre tudo o que o pai promete; quem usa não percebe a troca.
I · Segregação de Interfaces
Contratos pequenos; ninguém promete o que não faz.
D · Inversão de Dependência
A regra de negócio depende de um contrato; o detalhe técnico se adapta a ele.
Injeção de dependência
Receber as peças prontas (pelo construtor) em vez de criá-las lá dentro.
Dublê de teste
Objeto que substitui o de verdade só no teste, como o NotificadorDeTeste.
Exceção
Sinal de erro que interrompe a operação. UnsupportedOperationException: “não faço isso”.
List<Livro>
Uma lista que só aceita livros. O tipo entre < e > diz o que ela guarda.
Lambda
Um pedaço de código entregue como valor: () -> .... Digite hífen e maior que, nunca o símbolo →.
Padrão de projeto
Solução repetida que ganhou nome. Strategy: uma classe por jeito de fazer, atrás de um contrato.
Maven Wrapper
O mvnw: baixa e roda a versão certa do Maven sem instalar nada.
