Capítulo 04 · SOLID na prática

SOLID na mão

Um projeto pequeno em Java puro: a Biblioteca do Bairro. Cada letra do SOLID resolve um pedido da Dona Marta. Você vê o problema acontecer, digita a mudança e roda o mesmo teste de novo.

☕ Java 21 puro🧱 5 letras, 5 passos⌨️ você digita🧪 testes prontos🤖 agente só revisa
Meta da tarde: sair do projeto que “faz tudo num lugar” para um em que cada pedido novo é um arquivo novo, com os testes caindo de 4 s para 0,03 s.
📚
A biblioteca da Dona Marta [01]
Um programa que funciona, mas sofre a cada pedido novo

A Dona Marta cuida da biblioteca do bairro. Um sobrinho fez um programa em Java para o balcão: empresta livros, recebe devoluções, cobra multa por atraso e manda um aviso por e-mail. Funciona e os testes passam. Mas cada pedido novo vira um susto: o visitante paga multa zero, o dicionário não pode sair da sala, chegam e-books, e os testes demoram porque esperam um e-mail de mentira.

SOLID são cinco conselhos para organizar classes de modo que um pedido novo caia num lugar só do código. Hoje vamos aplicar um conselho por vez, no mesmo projeto, escrevendo o código à mão.

S · uma responsabilidade

A multa ganha a sua própria classe.

O · aberto/fechado

Chega o Visitante sem mexer no que funciona.

L · Liskov

O dicionário não pode fingir que é livro.

I · interfaces pequenas

O e-book não promete o que não faz.

D · inversão de dependência

O aviso vira uma tomada.

💡
A frase do dia: uma mudança, um lugar. Cada pedido da Dona Marta deveria cair num lugar só do código. As cinco letras são cinco jeitos de cumprir essa frase.

S · Uma classe, um motivo para mudar [03]
A multa sai do balcão e ganha uma classe própria
A ideia

O método devolver() da Biblioteca calcula a multa e manda o aviso. Quem decide a multa é a coordenação; quem decide o aviso é a TI. Duas pessoas mexendo no mesmo método: um conserto numa coisa pode quebrar a outra.

Regra: separe o código por quem pede a mudança.

CalculadoraDeMulta.java · arquivo novo⌨️ digite
public class CalculadoraDeMulta {

    public int calcular(Leitor leitor, int diasDeAtraso) {
        if (leitor.getTipo().equals("ALUNO")) {
            return diasDeAtraso * 100;
        }
        if (leitor.getTipo().equals("PROFESSOR")) {
            return diasDeAtraso * 50;
        }
        return 0;
    }
}

Na Biblioteca, apague o bloco do int multa = 0; até o fim do if/else e escreva as duas linhas acesas:

Biblioteca.java · como fica⌨️ linhas acesas
public class Biblioteca {

    private final CalculadoraDeMulta calculadora = new CalculadoraDeMulta();

    public void emprestar(Livro livro) {
        livro.emprestar();
    }

    public int devolver(Livro livro, Leitor leitor, int diasDeAtraso) {
        livro.devolver();

        int multa = calculadora.calcular(leitor, diasDeAtraso);

        if (multa > 0) {
            EmailSmtp email = new EmailSmtp();
            email.enviar(leitor.getEmail(), "Multa de " + multa + " centavos por " + diasDeAtraso + " dia(s) de atraso.");
        }
        return multa;
    }
}

O · Crescer sem mexer no que funciona [04]
Chega o Visitante: um arquivo novo, nenhuma classe antiga aberta
A ideia

Com if (tipo.equals("ALUNO")), cada tipo novo de leitor obriga a abrir a calculadora e editar no meio dela. E um tipo esquecido cai no return 0: paga zero, em silêncio.

A saída é uma interface: um contrato, a lista de métodos que uma classe promete ter. Cada tipo de leitor vira uma classe que cumpre o contrato (implements) e sabe a própria multa.

Regra: o código fica aberto para crescer e fechado para edição: tipo novo é arquivo novo.

interface

Só a promessa: o método sem corpo.

implements

“Eu cumpro esse contrato.” Esqueceu o método? Não compila.

@Override

“Este método vem do contrato.” O compilador confere o nome.

Agora o Leitor guarda um TipoDeLeitor no lugar do texto, e a calculadora vira uma linha:

L · O filho cumpre a promessa do pai [05]
O dicionário que quebrou a lista da turma
A ideia

class LivroDeConsulta extends Livro é herança: a classe filha é um tipo especial do pai, e onde o programa espera um Livro ele aceita a filha. Por isso a filha precisa cumprir tudo o que o pai promete. O Livro promete: “disponível, emprestar() funciona”.

Regra: se a filha não consegue cumprir a promessa do pai, ela não é filha. Não herde.

D · Dependa do contrato, não do detalhe [07]
O aviso vira uma tomada, e o teste pluga um dublê
A ideia

Dentro da Biblioteca há um new EmailSmtp(): o e-mail está soldado na regra, como um abajur com o fio preso na parede. Por isso o teste espera 2 s e não consegue conferir o aviso.

A saída: a Biblioteca depende de um contrato (Notificador) e recebe o notificador pronto pelo construtor. Quem monta (o App) pluga o e-mail; o teste pluga um dublê que só anota.

Regra: a regra depende do contrato; quem monta escolhe o detalhe.

BugZilla: os erros clássicos de SOLID [08]
Quatro jeitos de errar que você vai ver por aí (e em sugestões de agente)
🐛 Interface para cada classe

ILivro, ILeitor, cada uma com uma implementação só. Interface paga quando há mais de um jeito de cumprir ou uma troca real (como o dublê do teste).

🐛 Mais um if por tipo

else if (tipo.equals("PARCEIRO")) de novo. Cada caso novo edita o arquivo que funcionava. Fere o O.

🐛 Filha que não cumpre

emprestar() que lança exceção ou não faz nada. Fere o L. Não herde: crie outra classe.

🐛 new do detalhe dentro da regra

new EmailSmtp() dentro da Biblioteca. Fere o D. Receba pelo construtor; quem monta escolhe.

💡
E o contrário também é erro: separar demais. S não é “um método por classe”, e dois casos que nunca vão crescer cabem num if. SOLID são conselhos para uma dor real.
