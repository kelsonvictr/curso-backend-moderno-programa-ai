1. Preparar

20 minAbrir na aula ↗

Diga: “Primeiro vamos conferir a bancada. O agente precisa estar dentro do projeto certo.”

  1. Initializr: Maven, Java 21, versão estável do Spring Boot. Group br.com, Artifact pedidos, package br.com.pedidos. Adicionar somente Spring Web.
  2. IntelliJ: abrir a pasta do ZIP extraído, esperar a importação e selecionar JDK 21.
  3. Terminal do IntelliJ: abrir claude ou codex; colar o diagnóstico abaixo. O agente executa o Maven Wrapper.

Só avance se: pasta correta, Java 21 e teste inicial passando.

Se travar: Java diferente: conferir SDK e JAVA_HOME. Erro de DataSource: JPA entrou antes da hora. Voltar ao projeto com Spring Web.

Diagnosticar antes de começar
Ler prompt completo
Estamos na aula de uma API de pedidos. Inspecione a pasta atual e confirme que é a raiz do projeto gerado no Spring Initializr.
Confira Java 21 no terminal, a versão no pom.xml, Maven Wrapper e Git. Confirme que só adicionamos Spring Web como dependência funcional; testes do gerador são esperados. Não precisamos de banco ainda.
Execute o teste inicial usando o Maven Wrapper adequado ao sistema. Não altere código-fonte nem adicione dependências. Se houver erro, explique a causa e proponha a menor correção antes de editar.
Mostre: pasta, versões, comando executado e resultado real do teste. Não diga que passou sem executar. Pare aqui.

2. Ver responder

25 minAbrir na aula ↗

Diga: “Eu descrevo uma entrega pequena. O agente escreve e testa. Nós conferimos no navegador.”

  1. Enviar o prompt. Conferir o plano: uma rota GET /ola, um Controller simples e teste. Autorizar com o OK do topo.
  2. Pedir para executar testes e iniciar a aplicação. Abrir http://localhost:8080/ola (ou a porta informada).
  3. Apontar no arquivo: @RestController recebe chamadas web; @GetMapping liga GET à rota; return devolve o texto.

Lembrete: HTTP é o protocolo da conversa. GET pede uma resposta. Status 200 indica sucesso. Diff mostra o que mudou num arquivo.

Só avance se: apareceu API funcionando no navegador e os testes passaram.

Se travar: Conexão recusada: aplicação/porta. 404: rota ou pacote do Controller. Porta ocupada: identificar a instância antes de encerrar.

Criar nossa primeira resposta
Ler prompt completo
Queremos comprovar que a aplicação funciona antes de construir pedidos.
Proponha um plano curto para criar GET /ola, retornando exatamente "API funcionando", com HTTP 200. Use um OlaController simples dentro do pacote br.com.pedidos e um teste apropriado à versão do Spring Boot do pom.xml.
Não adicione banco nem dependências. Explique as anotações usadas em linguagem iniciante. Aguarde meu OK antes de implementar.
Depois do OK: se esta pasta ainda não tiver repositório Git próprio, inicialize um aqui para acompanhar as mudanças. Não altere outros repositórios. Implemente, execute os testes pelo Maven Wrapper, inicie a aplicação, faça a chamada HTTP real e mostre a resposta. Deixe a aplicação disponível para eu abrir no navegador e informe a URL. Mostre arquivos novos e diff dos modificados.

3. Orientar o agente

25 minAbrir na aula ↗

Diga: “O prompt é a tarefa de agora. O arquivo de instruções guarda nosso jeito de trabalhar.”

  1. Enviar o prompt dos documentos. Conferir: Java 21, Wrapper, passos pequenos, testes e respeito ao escopo.
  2. Autorizar somente os documentos. Abrir AGENTS.md e CLAUDE.md; este usa @AGENTS.md nesta aula.
  3. Pedir que o agente leia os dois e explique quais regras seguirá.

Pergunte: “Onde fica ‘usar Java 21 em todas as tarefas’?” Resposta: nas instruções permanentes, em AGENTS.md.

Só avance se: os arquivos existem e o agente resumiu o combinado; nenhuma funcionalidade foi criada.

Se travar: Pedir leitura explícita dos arquivos. Não presumir que uma sessão já aberta recarregou as instruções.

Registrar os combinados do projeto
Ler prompt completo
Proponha os dois documentos abaixo e aguarde meu OK antes de gravar. Depois do OK, crie AGENTS.md na raiz com estas regras, em português simples:
- Usar Java 21 e respeitar a versão do Spring Boot no pom.xml.
- Usar o Maven Wrapper do projeto para executar testes e aplicação.
- Trabalhar em passos pequenos: explicar o plano, aguardar meu OK, implementar, testar e apresentar evidência real.
- Não adicionar bibliotecas, funcionalidades ou infraestrutura fora da tarefa aprovada.
- Manter as regras do pedido em Java puro, sem Spring nem JPA nessas classes. JPA é a tecnologia de mapeamento para banco que só entra no final. Vamos introduzir essa separação gradualmente.
- Antes de cada tarefa, ler a especificação indicada no prompt. Não presumir que uma pasta .specs é lida automaticamente.
- Mostrar arquivos novos, diff dos arquivos modificados e o que não conseguiu verificar. Não apagar mudanças existentes.
Crie CLAUDE.md contendo @AGENTS.md, para importar essas instruções no Claude Code.
Se esses arquivos já existirem, preserve as instruções válidas e mostre conflitos antes de substituir qualquer conteúdo.
Nesta tarefa, altere somente esses documentos. Ao terminar, leia ambos e resuma o combinado que seguirá. Não implemente funcionalidades.

4. Escrever a spec

25 minAbrir na aula ↗

Diga: “Spec é o combinado da entrega. Ela precisa dizer como vamos reconhecer que deu certo.”

  1. Mostrar a criação da pasta .specs/ na simulação do capítulo.
  2. Enviar o prompt. Revisar os documentos propostos e autorizar a gravação, sem código Java.
  3. Abrir .specs/02-criar-pedido.md. Ler com a turma: 2 × 18,90 = 37,80; quantidade zero e lista vazia são rejeitadas.

Lembrete: SDD = desenvolvimento guiado por especificação. A pasta é uma convenção; o agente lê a spec porque mandamos. SKU é o código do produto; UUID é o identificador gerado para o pedido.

Só avance se: entrada, regras, resultado esperado e limites estão claros. Sem pagamento, frete ou estoque.

Se travar: Se o agente começar classes: “Pare. Nesta etapa, só os documentos”. “Cadastro bom” é vago; troque por exemplo verificável.

Criar a spec do cadastro
Ler prompt completo
Leia AGENTS.md. Vamos especificar o cadastro de pedidos, sem implementar Java ainda. Proponha os documentos abaixo e aguarde meu OK para gravá-los.
Crie .specs/README.md explicando que a pasta guarda decisões e que a spec relevante deve ser lida explicitamente em cada tarefa.
Crie .specs/02-criar-pedido.md com objetivo, entrada, regras, exemplos, limites e critérios de aceite:
- Entrada: uma lista de itens. Cada item tem sku, quantidade inteira e precoUnitario decimal.
- Rejeitar lista nula/vazia, item nulo, SKU nulo/em branco, quantidade menor ou igual a zero e preço nulo, zero ou negativo.
- Nesta aula, preço tem no máximo duas casas decimais. Rejeitar mais casas, sem arredondar silenciosamente.
- Gerar um identificador UUID para o pedido, iniciar com status ABERTO e calcular total a partir dos itens. O cliente não informa o total.
- Exemplo válido: CAFE-500, quantidade 2, precoUnitario 18.90; total 37.80.
- Exemplos inválidos: lista vazia e quantidade 0; não salvar pedido inválido.
- Primeiro faremos regras e testes em Java puro; depois cadastro em memória e entrada HTTP. Banco somente na etapa seguinte aprovada.
- No HTTP: POST /pedidos válido retorna 201 com id, status e total; regra inválida retorna 422 com mensagem clara; JSON malformado retorna 400.
- Fora do escopo: autenticação, pagamentos, frete, estoque, filas e atualização de pedidos.
Use linguagem curta, com exemplos. Ao terminar, mostre os documentos para revisão. Não crie código.

5. Construir em memória

65 minAbrir na aula ↗

Diga: “Vamos construir uma peça de cada vez. A regra do pedido existe antes do site e do banco.”

5.1 · Regra → domínio

Diga: “Pedido calcula; ItemPedido guarda quantidade e preço. Testamos essa conta sem ligar o banco.”

Faça: prompt “regras e testes” → plano → OK. Peça para apontar o teste de 37,80 e a rejeição de quantidade zero. Confira: Java puro, sem Spring/JPA nessas classes.

Rodada 1 · regras e testes
Ler prompt completo
Leia AGENTS.md e .specs/02-criar-pedido.md. Faça um plano apenas para as regras do pedido e seus testes em Java puro; aguarde meu OK.
Crie ItemPedido e Pedido em br.com.pedidos.domain. Classes simples, campos privados e métodos com nomes claros. Valide todas as entradas previstas na spec, incluindo nulos. Não permita que alterações na lista recebida contornem as regras. Calcule o total com BigDecimal a partir dos itens; não receba total pronto. Gere UUID e status ABERTO.
Use uma exceção específica de regra do pedido, explicando que exceção sinaliza uma operação que não pode continuar. Não importe Spring, JPA ou classes de HTTP no domínio. Não crie Controller, banco nem portas ainda.
Depois do OK, implemente e execute testes do domínio: exemplo 37.80, lista vazia, quantidade zero, demais entradas inválidas e soma de mais de um item. Explique um teste linha por linha. Mostre evidência real e pare.

5.2 · Processo → caso de uso, portas e memória

Diga: “O caso de uso coordena criar e salvar. A porta é o contrato. O adaptador de memória executa o armazenamento.”

Faça: prompt “caso de uso e memória” → plano → OK. Mostre Pedidos.salvar e PedidosEmMemoria. Confira: inválido não chama salvar.

Rodada 2 · caso de uso e memória
Ler prompt completo
Leia AGENTS.md e .specs/02-criar-pedido.md; inspecione o domínio existente. Proponha um plano para coordenar criar e salvar em memória; aguarde meu OK.
Em application.port.in, defina a interface CriarPedido e um comando Java simples com os dados necessários, sem tipos HTTP.
Em application.port.out, defina Pedidos com a operação salvar(Pedido pedido).
Em application, implemente CriarPedidoService: receber dados, construir o domínio, salvar pela porta Pedidos e devolver o pedido. Receba Pedidos pelo construtor, sem anotação Spring. Não duplique as validações do domínio.
Em adapter.out.memory, implemente PedidosEmMemoria, guardando pedidos por UUID em uma coleção segura para chamadas concorrentes. Não apenas finja que salvou.
Nesta rodada, nada de HTTP novo, JPA ou banco. Teste o caso de uso com uma implementação de teste da porta: pedido válido é salvo; pedido inválido não chama salvar. Teste também o armazenamento em memória.
Depois do OK, execute os testes pelo Wrapper, mostre quem chama cada interface, os arquivos criados e pare.

5.3 · Entrada web → Controller e montagem

Diga: “O Controller traduz JSON para dados Java. O caso de uso chama a regra e pede para salvar.”

Faça: prompt “POST /pedidos” → plano → OK. Peça chamadas reais: 201 / 37,80, quantidade zero 422, lista vazia 422, JSON quebrado 400.

Rodada 3 · POST /pedidos funcionando
Ler prompt completo
Leia AGENTS.md e .specs/02-criar-pedido.md e reutilize as peças existentes. Proponha somente a entrada HTTP e a montagem dos objetos; aguarde meu OK.
Crie PedidoController em adapter.in.web. POST /pedidos recebe DTO com itens (sku, quantidade, precoUnitario), converte para o comando Java e chama CriarPedido. Retorne DTO com id, status e total, HTTP 201.
Mapeie a exceção de regra do domínio para HTTP 422 e mensagem clara na borda web. JSON malformado retorna 400. Não exponha rastros internos de erro. Valores nulos devem seguir os critérios da spec, sem NullPointerException virar 500.
Em config, conecte PedidosEmMemoria e CriarPedidoService com @Bean. Mantenha domínio e aplicação sem imports de Spring/JPA. Uma única instância do armazenamento atende às requisições. Preserve GET /ola.
Depois do OK: implemente, execute testes automatizados, inicie ou reinicie apenas a aplicação desta aula e faça chamadas HTTP reais: válido (201, ABERTO, total 37.80); quantidade zero (422); lista vazia (422); JSON malformado (400).
Mostre requisição, status e corpo de cada resposta. Inspecione também o armazenamento no teste: inválidos não foram salvos. Explique o caminho de uma chamada apontando os arquivos, um por vez. Não adicione banco nem dependências novas.
Cola rápida: quem faz o quê na hexagonal?
Domínio — Pedido / ItemPedido
Regras: validar dados e calcular total. Não conhece Spring, web nem banco.
Caso de uso — CriarPedidoService
Coordena a ação: construir pedido válido e pedir para salvar.
Porta de entrada — CriarPedido
Interface com a operação que a aplicação oferece.
Porta de saída — Pedidos
Interface com a operação de que a aplicação precisa: salvar.
Adaptador — Controller / PedidosEmMemoria
Conecta o núcleo à web ou ao armazenamento.
DTO
Transporta os dados da entrada/saída web.
Configuração / injeção
Entrega o colaborador ao objeto: o caso de uso recebe quem sabe salvar.

Por que hexagonal? O núcleo fala por contratos e não depende da tecnologia externa. O hexágono não significa seis camadas.

Cuidado: ordem de chamadas não é direção dos imports. O caso de uso chama salvar pela interface; não importa a classe de memória.

Mostre: simulação do pedido com quantidade 2 e depois 0. O inválido para antes de salvar.

Só avance se: a chamada real funcionou e você consegue apontar a regra, o caso de uso e quem salva.

Se travar: Muitas classes: pedir um arquivo por vez no caminho da requisição. Erro 500 no inválido: conferir tradução da exceção para 422. Banco apareceu: voltar ao escopo em memória.

6. Salvar no PostgreSQL

55 minAbrir na aula ↗

Diga: “Vamos trocar onde guardamos o pedido. A regra que calcula 37,80 deve continuar igual.”

  1. Antes do código: mostrar na simulação que memória perde dados ao reiniciar e PostgreSQL os mantém.
  2. Prompt do banco: diagnóstico → plano → OK → Compose saudável e consulta SQL real. Porta e credenciais devem corresponder à conexão.
  3. Prompt do adaptador: plano → OK → JPA e driver → adaptador e configuração. Domínio e caso de uso continuam sem JPA.
  4. Prova: cadastrar, anotar UUID, consultar no banco, reiniciar só a aplicação e consultar o mesmo UUID. Conferir testes e rejeição sem novo registro.

Lembrete: container executa o banco; volume guarda arquivos; SQL consulta dados; JPA mapeia objetos para tabelas. Porta 5432 é de rede, diferente da interface chamada “porta” na arquitetura.

Só avance se: o mesmo pedido permanece no banco após o reinício, com itens corretos e testes passando.

Se travar: Conexão: container, porta, senha e configuração carregada. Dois beans: escolher um adaptador de Pedidos. Não apagar volumes para tentar resolver.

Planejar a troca e preparar o banco
Ler prompt completo
Leia AGENTS.md e a spec do cadastro. Vamos trocar a implementação de armazenamento, preservando comportamento e núcleo.
Primeiro confira se Docker Desktop está ativo, Docker Compose está disponível e se a porta local pretendida está livre. Não encerre serviços de outros projetos.
Proponha .specs/03-persistencia.md com plano e critérios: persistir pedido e itens em PostgreSQL; preservar as regras e respostas HTTP; reiniciar a aplicação e consultar no banco o mesmo UUID. Não apague pedidos existentes.
Nesta rodada, após meu OK, crie somente a spec, compose.yaml e configuração local de credenciais e uma regra em .gitignore para que esse arquivo não entre no Git. Use PostgreSQL 17, projeto Compose identificado como pedidos-aula, porta ligada a 127.0.0.1, volume nomeado e healthcheck. Se a porta 5432 estiver ocupada, proponha outra porta no host.
Inicie somente esse serviço e aguarde ficar saudável. Mostre o status e execute uma consulta SQL simples para comprovar conexão. Explique container, volume e porta em linguagem iniciante.
Não adicione JPA nem mude código Java nesta rodada. Não use limpeza global de Docker nem remova volumes. Aguarde meu OK antes de criar arquivos e iniciar o banco.
Conectar o adaptador e provar persistência
Ler prompt completo
Leia AGENTS.md, .specs/02-criar-pedido.md e .specs/03-persistencia.md. O PostgreSQL da aula já está saudável. Proponha o plano e aguarde meu OK.
Adicione Spring Data JPA e o driver PostgreSQL compatíveis com a versão atual do pom.xml. Não troque versões do projeto. Configure conexão usando a configuração local ignorada pelo Git; explique como carregá-la na execução e nos testes.
Crie entidades de persistência e repository JPA dentro de adapter.out.jpa. Persista UUID, status e os itens (sku, quantidade, precoUnitario) de forma atômica; use tipo decimal para preço. Total continua calculado pelos itens, sem coluna de total.
Crie PedidosJpaAdapter implementando a porta Pedidos. Faça conversão explícita entre domínio e persistência, sem anotações JPA no domínio. Troque a montagem da aplicação para injetar apenas esse adaptador, evitando dois beans concorrentes para Pedidos. Preserve o adaptador em memória para testes.
Não altere domínio nem caso de uso para acoplar banco. Mantenha suas regras e testes. Para este banco local de aula, ddl-auto=update pode criar as tabelas; registre que produção exige migrações versionadas.
Depois do OK: execute os testes existentes e testes de integração da persistência. Use dados de teste identificáveis e limpe apenas esses dados, sem truncar tabelas ou apagar registros manuais.
Faça POST real com CAFE-500, quantidade 2, preço 18.90: confira 201 e 37.80. Registre o UUID retornado e consulte pedido e itens no PostgreSQL.
Reinicie somente a aplicação, mantendo banco e volume. Consulte novamente o mesmo UUID e confira os itens e o total calculado 37.80. Demonstre que quantidade zero é recusada sem novo registro.
Mostre os comandos executados, respostas, consultas, testes e diff. Se algo não rodou, informe claramente. Pare sem publicar ou apagar recursos.
