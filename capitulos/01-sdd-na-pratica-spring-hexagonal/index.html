A história do pedido 4711
Por que passamos uma tarde inteira construindo o que "qualquer tutorial faz em vinte minutos"
Era uma terça-feira comum quando o pedido 4711 entrou. Um cliente, três itens, cartão aprovado. O serviço fez o que sempre fazia: salvou no banco, chamou o estoque, mandou o e-mail, gerou a nota. Só que naquela terça o servidor de e-mail ficou fora do ar por quatro minutos. O pedido 4711 falhou inteiro. O estoque já tinha baixado. O cliente viu "erro" na tela e comprou de novo. Dois pedidos, duas cobranças, uma reclamação, e um sábado do time de plantão.

Ninguém nesse sistema errou a sintaxe. Todo teste unitário passava. O erro era de julgamento: alguém decidiu, provavelmente sem perceber, que mandar um e-mail fazia parte de criar um pedido. E alguém decidiu que o total de um pedido era um double guardado numa coluna, e que o status era uma String. Decisões pequenas, tomadas por default, que viraram incidente.

Hoje a IA escreve a sintaxe. Ela também toma esses defaults, e toma exatamente os mesmos, porque aprendeu com milhares de serviços iguais ao do pedido 4711. O que sobra para você é decidir antes de o código existir. É isso que SDD significa na prática: a spec é o lugar onde a decisão é tomada; o código é consequência. E é isso que hexagonal significa na prática: um jeito de organizar o serviço em que "mandar e-mail" e "salvar no Postgres" ficam do lado de fora, atrás de uma porta, e o pedido no centro não sabe que eles existem.

Nesta tarde construímos, do zero, o serviço que teria salvado o pedido 4711. Não o sistema inteiro: o primeiro tijolo, feito do jeito certo. Ele cresce nos sete sábados seguintes até rodar na AWS. Cada decisão que hoje parece cerimônia demais para um CRUD vai se pagar num sábado específico, e o capítulo diz qual.

O CLAUDE.md seção a seção, e por que ele vem antes do código

No Cap 0 você viu que regra dita na conversa cai da mesa. Aqui a consequência prática: o primeiro commit do projeto não é código, é o contrato. Quatro seções, cada uma respondendo a uma pergunta que o agente faria se pudesse:

  1. Stack e comandos ("com o que eu trabalho e como rodo?"): Java 21, Spring Boot 3, Maven wrapper, Postgres via compose. Os comandos exatos: ./mvnw test, docker compose -f infra/docker-compose.yml up -d.
  2. Arquitetura ("onde cada coisa mora?"): os pacotes do hexagonal e a regra da dependência. É a seção que mais evita retrabalho, porque o default do agente é o tutorial de três camadas com @Entity no domínio.
  3. Convenções ("como se escreve aqui?"): imutabilidade, BigDecimal, exceções nomeadas, sem Lombok, sem dependência nova sem pedir.
  4. Como trabalhar ("qual é o ritual?"): ler a spec em .specs/, propor plano, esperar OK, rodar testes antes de dizer pronto, não criar arquivo fora do pedido.

A pasta .specs/ começa com um README.md de cinco linhas dizendo o que o serviço é e uma spec por tarefa. No fim do curso ela tem a história inteira das decisões, datada. É a memória que sobrevive ao contexto, ao colega novo e a você mesmo daqui a três meses.

Permissões. O Claude Code pergunta antes de rodar comandos. Hoje vocês liberam permanentemente o que é seguro e repetitivo (./mvnw, docker compose, git status/diff) e deixam o resto perguntando. Ler o pedido de permissão é parte da revisão: se ele quer rodar npm install, algo já saiu do trilho.

CLAUDE.md — a versão do professor (a sua pode divergir; o que importa é ser verificável)md
# Serviço de Pedidos — regras da casa

## Stack e comandos
- Java 21, Spring Boot 3, Maven. Sempre `./mvnw`, nunca `mvn`.
- Postgres 16 em Docker: `docker compose -f infra/docker-compose.yml up -d`. Porta 5432, db/user/senha `pedidos`.
- Testes: JUnit 5. `./mvnw -q test` antes de dizer que terminou.

## Arquitetura: hexagonal (ports & adapters)
- `br.com.pedidos.dominio`   records, regras, exceções de domínio. Não importa nada de Spring/JPA/web.
- `br.com.pedidos.aplicacao` casos de uso (ports de entrada) e ports de saída (interfaces). Também não importa framework.
- `br.com.pedidos.adapters`  `entrada.rest` (controllers, DTOs) e `saida.jpa` (entidade JPA, repositório Spring Data, mapper).
- `br.com.pedidos.config`    classes @Configuration que ligam ports a adapters com @Bean.
- Dependências apontam para dentro: adapters conhecem aplicacao e dominio; o inverso nunca.

## Convenções
- Domínio imutável: records + List.copyOf. Sem setter. Transição de estado é método que devolve novo objeto.
- Dinheiro é BigDecimal. Identidade é String (UUID).
- Violação de regra = exceção de domínio nomeada (PedidoFechadoException). Nunca null, nunca boolean de erro.
- Sem Lombok. Sem MapStruct. Não adicione dependência ao pom sem me perguntar.

## Como trabalhar
- Antes de codar: leia a spec em .specs/ e proponha um plano curto (arquivos + testes). Só execute após meu "ok".
- Não crie arquivo que a spec não pede. Sem README, Dockerfile, DTO extra ou "melhorias".
- Ao terminar, liste os arquivos tocados e explique cada decisão de design em uma frase.

Spec verificável, e o Java que vira critério

Uma spec tem quatro partes (Cap 0): contexto, tarefa, regras, definição de pronto. O que faz dela uma spec de sênior é que cada linha da seção de regras é um item de checklist de revisão. Para o domínio de Pedidos, as regras vêm do Java moderno que um sênior espera ver, e cada uma tem um porquê que o pedido 4711 explica:

  • Imutável, com record e cópia defensiva. Criou, não muda. Um pedido que passa por uma fila (Bloco 2) ou por duas threads não pode ser alterado por quem tem a referência. List.copyOf no compact constructor fecha a brecha da lista.
  • Total derivado, nunca armazenado. Duas fontes da verdade desatualizam. O 4711 tinha total guardado.
  • Dinheiro é BigDecimal. double em dinheiro é erro de arredondamento esperando a auditoria.
  • Status é tipo fechado (enum hoje, sealed quando houver dados por variante). String aceita "PAGOO". O switch exaustivo garante que um status novo quebra a compilação, não a produção.
  • Regra violada é exceção de domínio nomeada. PedidoFechadoException diz o que aconteceu; IllegalStateException diz que algo aconteceu. Nunca null, nunca boolean de sucesso.
  • Transição de estado é método que devolve novo objeto. pedido.pagar() retorna outro Pedido. Setter não existe.

Tudo isso cabe em dez linhas de spec. E tudo isso o agente não faz por padrão, porque a internet não faz.

De três camadas a ports & adapters

O Spring que a maioria aprendeu organiza o serviço em três camadas: Controller chama Service que chama Repository. Funciona, até o dia em que você precisa trocar o banco, testar a regra sem subir o contexto, ou publicar um evento em vez de chamar o e-mail. Aí descobre que a regra de negócio depende de @Entity, que o service conhece o JpaRepository, e que o teste do caso de uso precisa de um Postgres de pé.

✗ Três camadas, como o tutorial ensina
PedidoControllerPedidoService (regra + orquestração)PedidoRepository extends JpaRepository@Entity Pedido (domínio = tabela)

Tudo aponta para baixo, e o de baixo é o framework. A regra "só ABERTO paga" mora num if no service, ao lado do save() e do enviarEmail(). É o pedido 4711.

✓ Hexagonal (ports & adapters)
adapters/entrada/rest → PedidoControlleraplicacao → port CriarPedido · CriarPedidoServicedominio → Pedido, regras, exceçõesaplicacao → port Pedidos (interface)adapters/saida/jpa → PedidosJpaAdapter, PedidoJpaEntity

O centro (domínio + aplicação) não importa nada de fora. Quem entra (REST) e quem sai (JPA) são adapters que implementam ou chamam ports: interfaces definidas pelo centro.

port de entrada (driving)
interface CriarPedido { Pedido executar(Comando c); }
quem chama: o controller REST hoje, um consumidor de fila no Sáb 4, uma Lambda no Sáb 6

⬡ o núcleo

sem Spring, sem JPA, sem web

port de saída (driven)

port de saída (futuro)
interface PublicadorDeEventos { … }
Sáb 4: é por aqui que o e-mail do 4711 deixa de derrubar o pedido

A regra da dependência. Setas de import apontam para dentro. adapters conhece aplicacao e dominio; aplicacao conhece dominio; dominio não conhece ninguém. Quem liga a interface Pedidos à classe PedidosJpaAdapter é uma classe de configuração na borda (config/), com @Bean. O núcleo nunca vê a anotação.

O que isso paga, e quando.

  • Hoje: o teste de CriarPedidoService roda com um Pedidos em memória, em milissegundos, sem Spring. Testes rápidos são testes que rodam.
  • Sáb 3: Testcontainers testa só o adapter JPA contra um Postgres real; o núcleo continua sem banco.
  • Sáb 4: "avisar o estoque" vira um port de saída; o adapter publica numa fila. O caso de uso não muda uma linha.
  • Sáb 7: o port Pedidos ganha um adapter DynamoDB. O domínio e o serviço não sabem que mudaram de banco.

O que não fazer. Hexagonal não é criar interface para tudo. Um port existe quando há uma fronteira real (entrada externa, infraestrutura, algo que você quer trocar ou testar isolado). Pedido não precisa de IPedido. O agente adora criar interface demais; a spec diz quais existem.

O banco num container, e a entidade JPA como adapter

Por que Docker. Um Postgres instalado na máquina é um Postgres com versão, porta e senha diferentes em cada notebook da sala. O container é o mesmo binário, a mesma versão, a mesma configuração, descrito num arquivo versionado junto com o código. docker compose up -d sobe; down derruba; o volume guarda os dados entre reinícios. No Sáb 3 o Testcontainers vai subir um desses dentro do teste, e no Sáb 4 o RabbitMQ entra no mesmo arquivo.

A entidade JPA não é o domínio. É a tentação número um, e é o que o agente faz por padrão: colocar @Entity no Pedido. Só que JPA exige construtor vazio, campos mutáveis e proxies; o domínio exige o oposto. A solução hexagonal é ter dois objetos: PedidoJpaEntity (mutável, anotada, mora em adapters/saida/jpa) e o record Pedido. Um PedidoMapper converte nos dois sentidos. Parece duplicação; é isolamento. Quando a tabela mudar, o domínio não muda.

O adapter de saída implementa o port Pedidos usando um JpaRepository do Spring Data por dentro. O adapter de entrada é o controller: recebe JSON num PedidoRequest, monta o Comando, chama o port CriarPedido, devolve um PedidoResponse. Ele não sabe que existe banco.

Schema. Hoje deixamos o Hibernate criar as tabelas (ddl-auto: update) para a aula andar. Em produção isso é proibido; migração é com Flyway, e entra no Sáb 3 junto com o Testcontainers. Anote como dívida consciente.

src/main/resources/application.ymlyaml
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/pedidos
    username: pedidos
    password: pedidos
  jpa:
    hibernate:
      ddl-auto: update        # só hoje. Sáb 3: Flyway.
    open-in-view: false       # o adapter abre e fecha a sessão; o controller não
