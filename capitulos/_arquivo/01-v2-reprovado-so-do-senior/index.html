Você já programa em Java e Spring. Então vamos ser diretos: a partir de agora, a IA escreve a sintaxe por você. Isso não é ameaça — é a régua nova. O que o mercado passa a pagar é a habilidade de olhar um trecho de código e dizer, com vocabulário técnico, por que ele é bom ou ruim — e cobrar isso de quem (ou do que) escreveu.

A spec carrega a sua intenção

Uma spec ruim ("crie um serviço de pedido") devolve código genérico. Uma spec de sênior carrega as restrições que separam bom de ruim. Repare na diferença:

.specs/pedido.mdspec
# Domínio: Pedido
## Regras
- Pedido é imutável depois de criado (record + cópia defensiva das listas).
- Total é derivado dos itens, nunca armazenado; nunca negativo.
- Violação de regra lança exceção de domínio, não retorna null.
- O pacote de domínio não conhece Spring, JPA nem web.
## Definição de pronto
- Teste de unidade cobrindo item inválido e pedido vazio.
- Nenhum setter público no domínio.

Com essa spec, quando o agente devolver um Pedido com setter público ou um método retornando null, você tem onde se apoiar pra rejeitar. A spec virou o seu contrato de revisão.

CLAUDE.md — a memória do projeto

O CLAUDE.md na raiz do projeto é lido pelo agente em toda sessão. É onde moram as regras que valem pra tudo — pra você não repetir em cada prompt:

CLAUDE.mdmd
# Serviço de Pedidos — convenções
- Java 21, Maven. Domínio imutável: records + cópia defensiva. Sem setter no domínio.
- Dinheiro é BigDecimal. Erro de domínio = exceção própria (ex.: PedidoFechadoException). Nunca null.
- Camadas: Controller -> Service -> Repository. Dependências apontam pra dentro (domínio não importa framework).
- Testes: JUnit 5. Toda regra de domínio tem teste. Não criar arquivo fora do que a spec pede.
- Antes de codar, leia a spec em .specs/ e proponha um plano curto. Só execute depois do meu OK.
🧠
Contexto é um recurso escasso. O que entra no CLAUDE.md e na spec molda o output; o que você joga no prompt sem necessidade só dilui. Parte do julgamento de sênior é saber o que NÃO colocar no contexto:
✅ Entra
  • Convenções que valem pro projeto inteiro (CLAUDE.md)
  • A spec da tarefa atual, com critérios verificáveis
  • Os 2–3 arquivos que a tarefa toca (o agente lê o resto se precisar)
  • O erro real, colado inteiro, quando algo quebra
🚫 Não entra
  • "Cole o repositório inteiro" — dilui e custa contexto
  • Histórico de conversa velha sobre outra tarefa
  • Adjetivos ("faz bonito", "robusto") no lugar de critério
  • Segredos, chaves, dumps de banco

☕ Imutabilidade & record

O default de um domínio bem feito é imutável: criou, não muda. Menos bug de estado compartilhado, seguro entre threads (importa muito quando chegarmos em eventos). Antes do Java 16 isso custava boilerplate; hoje é uma linha.

Antes — POJO na mão (~40 linhas)java
public final class ItemPedido {
  private final String sku;
  private final int quantidade;
  public ItemPedido(String sku, int quantidade) { this.sku = sku; this.quantidade = quantidade; }
  public String getSku() { return sku; }
  public int getQuantidade() { return quantidade; }
  // + equals(), hashCode(), toString() na mão...
}
Agora — record (equals/hashCode/toString de graça)java
public record ItemPedido(String sku, int quantidade, BigDecimal precoUnitario) {
  public ItemPedido {                                   // compact constructor: valida na entrada
    if (quantidade <= 0) throw new ItemInvalidoException("quantidade");
  }
}
⚠️
Record não é imutável "de graça" quando tem coleção. Se um campo é List<ItemPedido>, o record guarda a referência — quem passou a lista pode mudá-la depois. Imutabilidade real pede cópia defensiva no compact constructor:
Pedido.java — cópia defensiva + total derivadojava
public record Pedido(String id, String clienteId, List<ItemPedido> itens, StatusPedido status) {
  public Pedido {
    itens = List.copyOf(itens);                     // imutável de verdade
  }
  public BigDecimal total() {                       // derivado, nunca armazenado
    return itens.stream()
        .map(i -> i.precoUnitario().multiply(BigDecimal.valueOf(i.quantidade())))
        .reduce(BigDecimal.ZERO, BigDecimal::add);
  }
  public Pedido adicionarItem(ItemPedido item) {       // devolve um NOVO pedido
    if (status != StatusPedido.ABERTO) throw new PedidoFechadoException(id);
    var novos = new ArrayList<>(itens); novos.add(item);
    return new Pedido(id, clienteId, novos, status);
  }
}
⌨️
A seta da lambda (i -> …) e do switch é dois caracteres: - seguido de >. Sua IDE pode desenhar → por causa de ligadura de fonte — é só visual.

🔒 sealed + pattern matching

Quando um tipo só pode ter um conjunto fechado de variações (o resultado de um pagamento, um evento), sealed diz isso ao compilador — e o switch com pattern matching fica exaustivo: esqueceu um caso, não compila. Adeus default que esconde bug.

ResultadoPagamento.javajava
sealed interface ResultadoPagamento permits Aprovado, Recusado, Estornado {}
record Aprovado(String pedidoId, BigDecimal valor) implements ResultadoPagamento {}
record Recusado(String pedidoId, String motivo)  implements ResultadoPagamento {}
record Estornado(String pedidoId) implements ResultadoPagamento {}

String descrever(ResultadoPagamento r) {
  return switch (r) {                       // exaustivo: o compilador cobra todos
    case Aprovado a  -> "ok: " + a.valor();
    case Recusado re -> "falhou: " + re.motivo();
    case Estornado e -> "estornado";
  };
}

Repare que isso já é um evento com três variantes. No Bloco 2, esse mesmo tipo vai passar por uma fila. Sealed + record é o formato natural de mensagem.

🎯 Optional sem abuso, enum rico, stream com parcimônia

Optional é para retorno que pode não existir — não para campo, nem parâmetro. Enum não precisa ser só uma etiqueta: pode carregar comportamento. E stream é ótimo até virar charada — um for claro vence um pipeline ilegível.

bom-vs-abuso.javajava
// OK: retorno que pode não existir
Optional<Pedido> buscarPorId(String id);

// ABUSO: Optional como campo (não faça)
private Optional<String> cupom;   // ❌

// Enum rico: a transição de status mora no próprio status
enum StatusPedido {
  ABERTO, PAGO, CANCELADO;
  boolean podeIrPara(StatusPedido novo) {
    return this == ABERTO && (novo == PAGO || novo == CANCELADO);
  }
}
🧭 Record cabe aqui?
Clique em cada cenário e forme seu veredito ANTES de revelar. (record ≠ bala de prata)
Cenário A
DTO de resposta da API
record PedidoResp(
  String id, BigDecimal total)
✅ CabeDado que entra e sai, sem comportamento e sem mutação. É o caso perfeito de record.
Cenário B
Entidade JPA gerenciada
@Entity
class PedidoEntity { ... }
🚫 Não cabeJPA exige construtor sem-arg e campos mutáveis pro proxy. Record é final e imutável — briga com o framework. (No Sáb 3, a entidade JPA vira um adapter; o domínio continua record.)
Cenário C
Evento de domínio
record PedidoCriado(
  String id, Instant em)
✅ CabeEvento é um fato que aconteceu — imutável por natureza. Record é ideal (e brilha no Bloco 2).

Anemic Domain Model
domínio sem comportamento, regra espalhada no service

O agente devolveu um Cliente que é só um saco de getters/setters, e jogou TODA a regra de negócio no service. Parece OO, mas é procedural fantasiado.

PR do agente — o que tem de errado?java
class Cliente {
  private String nome; private int pontos;
  public void setPontos(int p) { this.pontos = p; }   // qualquer um muda
  public int getPontos() { return pontos; }
}
class FidelidadeService {
  void pontuar(Cliente c, int compra) {
    if (compra > 0) c.setPontos(c.getPontos() + compra / 10);   // regra fora do dono
  }
}
🚨
PARE. Forme seu diagnóstico antes de abrir. Que princípio isso fere? Onde a regra deveria morar? Como você instruiria o agente a refatorar — em uma frase?
👀 Ver o diagnóstico + a refatoração-modelo ▼

Diagnóstico (nomeável): Anemic Domain Model — o dado (Cliente) não protege o próprio estado e a regra de pontuação vive no service. Sintomas: setter público deixando qualquer um corromper pontos; lógica de negócio (a fórmula) longe do dono do dado; o service viola SRP ao acumular regra que era do domínio.

Como dirigir o agente (1 frase): "Mova a regra de pontuação para dentro de Cliente como um método de comportamento, remova o setter de pontos e deixe o service só orquestrando."

Cliente.java — domínio ricojava
class Cliente {
  private String nome; private int pontos;
  public void pontuarPor(int compra) {        // regra mora com o dado
    if (compra > 0) this.pontos += compra / 10;
  }
  public int pontos() { return pontos; }      // sem setter: estado protegido
}
// Service agora só orquestra: cliente.pontuarPor(compra);

Repare: não é "a resposta certa". É o critério — comportamento junto do dado, estado protegido, service magro. Esse é o vocabulário que você usa pra revisar qualquer PR, humano ou agente. Sáb 2 é inteiro sobre isso.

Lab 1 — Dirigir o agente: o domínio Pedido
spec → plan → seu OK → execute → revisar linha a linha

Dentro do seu repositório pedidos, abra o Claude Code. Não digite o código você mesmo. Salve a sua spec em .specs/pedido.md (a que você escreveu em casa — ela está no 📓 Caderno) e dê a ordem:

claude · pedidos
> Leia .specs/pedido.md e o CLAUDE.md. Proponha um plano curto (arquivos e testes que vai criar). Não implemente ainda.

Leia o plano. É aqui que você corta o que ele inventou (um PedidoService que a spec não pediu, um PedidoRepository, um README). Só depois:

claude · pedidos
> Aprovado, sem o Service e sem o README. Implemente e rode os testes.

Na revisão, cobre:

  • Pedido e ItemPedido são record? Tem List.copyOf no compact constructor?
  • As exceções são de domínio (PedidoFechadoException) ou genéricas (IllegalStateException)? A spec dizia o quê?
  • total() é calculado ou virou campo? Dinheiro é BigDecimal?
  • adicionarItem devolve novo Pedido ou mutou a lista?
  • Alguma importação de Spring/JPA no pacote de domínio?
  • O agente criou algo fora da spec? (Quase sempre cria.)
🚨
Revise antes de abrir o olhinho. Anote no Caderno os 3 pontos que você mandou corrigir. É o entregável — e é o que a gente compara na sala.
👀 Ver a spec-modelo e os pontos de revisão que costumam aparecer ▼

Spec-modelo: é o esqueleto do editor de spec lá em cima (botão ✨). O que a torna boa não é o tamanho — é que cada linha é verificável: dá pra olhar o código e dizer "cumpre" ou "não cumpre".

O que o agente costuma fazer errado nessa tarefa (e que a sua revisão precisa pegar):

  1. Usa IllegalArgumentException em vez da exceção de domínio nomeada. Nomear a exceção é parte do vocabulário do sistema.
  2. Guarda total como campo do record "por performance". Não pediu, e agora tem dois lugares pra mesma verdade.
  3. Esquece o List.copyOf — o record parece imutável e não é.
  4. Coloca a transição de status num if no método em vez de perguntar ao enum (status.podeIrPara(PAGO)).
  5. Cria Service, Repository, README.md, às vezes um Dockerfile. A spec dizia "só o domínio".
  6. Testes que só cobrem o caminho feliz. A definição de pronto listava os casos de erro.

Cada item desses é uma frase de revisão: "A spec pede exceção de domínio; troque IllegalArgumentException por ItemInvalidoException." Curta, nomeada, apontando pra spec. É assim que se dirige.

Lab 2 — Revisar o PR
aponte as violações, nominalmente · treino do formato avaliativo do Sáb 2

Outro agente (o de um colega, digamos) abriu este PR no serviço de Pedidos. Encontre pelo menos 4 problemas e nomeie cada um (o nome importa — é o vocabulário que a avaliação cobra).

Pedido.java + PedidoService.java — PR do agentejava
public class Pedido {
  private String id;
  private List<ItemPedido> itens = new ArrayList<>();
  private double total;                                        // 1
  private String status = "ABERTO";                            // 2
  public List<ItemPedido> getItens() { return itens; }         // 3
  public void setTotal(double t) { this.total = t; }
  public void setStatus(String s) { this.status = s; }
  // getters...
}

public class PedidoService {
  public Pedido adicionarItem(Pedido p, ItemPedido i) {
    if (i == null) return null;                                // 4
    p.getItens().add(i);
    p.setTotal(p.getTotal() + i.getPreco() * i.getQtd());        // 5
    emailService.avisar(p);                                       // 6
    return p;
  }
}
🚨
Liste suas violações no Caderno antes de abrir. Dica: pense em quem é o dono da regra, tipo pra dinheiro, o que vaza pra fora, string onde devia ser tipo, null, e responsabilidades.
👀 Ver as violações esperadas ▼
  1. Anemic Domain Model (o PR inteiro): Pedido é um saco de setters; a regra de adicionar item e calcular total vive no service. A regra tem que morar com o dado (pedido.adicionarItem(i)).
  2. double para dinheiro (1, 5): erro de precisão clássico. Dinheiro é BigDecimal.
  3. Estado derivado armazenado (1, 5): total guardado e recalculado à mão — duas fontes da verdade, e uma delas vai desatualizar. Total é derivado dos itens.
  4. Encapsulamento quebrado / coleção mutável vazada (3): getItens() devolve a ArrayList interna; qualquer um faz add por fora. Devolva cópia imutável ou não devolva.
  5. Stringly typed (2): status como String aceita "PAGOO". É um conjunto fechado: enum (ou sealed).
  6. null como controle de fluxo (4): empurra NullPointerException pro chamador. Item nulo é violação de contrato: exceção.
  7. SRP quebrado / efeito colateral escondido (6): adicionar item envia e-mail. Não dá pra testar o método sem mandar e-mail — e no Bloco 2 esse acoplamento vira o motivo de existir uma fila.

Achou 4+ e nomeou? É exatamente o formato do lab avaliativo do Sábado 2 — lá com SOLID inteiro no checklist. Agora dirija a correção no seu repositório: "Refatore para domínio rico conforme .specs/pedido.md; remova o e-mail do adicionarItem."
