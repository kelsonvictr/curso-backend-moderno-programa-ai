Duas entradas, duas verdades? [03]

Uma proposta do agente protege apenas a API. O objeto tem campos privados, mas entrega a lista interna. Leia o trecho e preveja o que a importação faz com um pedido pago.

Java · trecho de leitura
// Trecho defeituoso do laboratório: não copiar para o serviço.
public void peloController(PedidoAnemico pedido, String sku) {
    if (pedido.isPago()) throw new IllegalStateException("Pedido fechado");
    pedido.getItens().add(sku);
}
public void pelaImportacao(PedidoAnemico pedido, String sku) {
    pedido.getItens().add(sku);
}
👀 Depois da previsão: o que acontece?

A importação adiciona o item. A condição só existe no controller e getItens() devolve a coleção mutável. private limita o acesso direto ao campo; não impede modificar o objeto que a referência aponta.

13:45 · Pausa teórica · encapsulamento

Objeto não é só uma sacola de campos [04]

Estado + comportamento

Estado é o que o objeto representa agora: itens e status. Comportamento é o que ele permite fazer: adicionar, pagar, cancelar. A classe define essa forma; cada objeto é uma ocorrência concreta.

Uma regra que deve permanecer verdadeira

Invariante é uma condição que as operações precisam preservar. Aqui: um pedido fechado não aceita novos itens. Essa promessa precisa valer para API, importação e chamada direta.

Encapsular é oferecer operações que preservam essa promessa e controlar como o estado é exposto. É como um caixa que permite uma retirada validada, sem entregar acesso irrestrito ao saldo. A comparação tem limite: a proteção depende de todas as operações públicas reais do código.

Pedido do Cap 01 · regra local + novo estado
public Pedido adicionarItem(ItemPedido item) {
    exigirAberto();
    var novosItens = new ArrayList<>(itens);
    novosItens.add(item);
    return new Pedido(id, clienteId, novosItens, status);
}

Domínio rico reúne dados e regras que pertencem ao negócio. Um modelo anêmico deixa essas decisões espalhadas nos serviços enquanto os objetos apenas recebem setters. Isso não transforma todo objeto de dados em erro: DTOs (Data Transfer Objects, objetos de transferência de dados) transportam informações e não precisam se tornar entidades de domínio.

Pedido decide se pode mudar. O caso de uso busca, pede a mudança e salva. O domínio não abre conexão HTTP, não envia e-mail e não chama JPA.

Ainda no Ato 1 · referências e cópia defensiva

Record não congela tudo sozinho [06]

O record fixa as referências dos componentes. Se um componente aponta para uma lista mutável, outra pessoa ainda pode mudar essa lista. Imutabilidade superficial é diferente de congelar todo o grafo de objetos.

Recorte para explicar a cópia · não substitui o Pedido completo
public record Pedido(List<ItemPedido> itens) {
    public Pedido {
        itens = List.copyOf(itens);
    }
}

List.copyOf produz uma lista não modificável com os elementos atuais. Alterar a lista de origem depois não muda essa lista. Os elementos continuam sendo referências: se fossem mutáveis, poderiam mudar por dentro. No nosso caso, ItemPedido usa String, int e BigDecimal, sem componentes mutáveis.

Adicionar um item cria outro Pedido; quem chamou precisa usar o retorno. Imutabilidade facilita raciocinar, mas não impede duas requisições concorrentes de sobrescrever dados. Isso pede outra decisão de persistência.

A origem recebe um novo item depois da construção com List.copyOf. O Pedido deve mudar?

O que deve mudar junto? [08]

Um teste unitário verifica um comportamento sem exigir a aplicação inteira ou serviços externos. Um fake é uma implementação simples usada no teste, como um repositório em memória. Ele permite observar o contrato; não prova que o banco real funciona. Essa segunda evidência vem do teste de integração.

Coesão descreve quanto as partes de um módulo colaboram para uma responsabilidade clara. Acoplamento descreve quanto uma parte depende de outra. Precisamos de colaboração; o objetivo é tornar as dependências deliberadas e as mudanças compreensíveis.

Juntar pelo mesmo motivo

Adicionar, pagar e cancelar preservam o ciclo de vida de Pedido. Ter vários métodos não torna a classe ruim. Eles operam o mesmo estado e suas regras.

Separar por mudança independente

A equipe comercial altera cálculo; comunicação altera a mensagem; infraestrutura altera a conexão. Uma edição de texto não deveria exigir revisar a regra monetária.

Um método curto pode estar no lugar errado. Um arquivo grande pode conter uma responsabilidade coesa. Procure o motivo e o efeito da mudança, não um limite mágico de linhas.

Composição, herança e polimorfismo

Reutilizar não exige virar um subtipo [09]

Herança cria uma relação de subtipo: quem espera a classe base também pode receber a derivada. Reaproveitar algumas linhas não basta para justificar essa promessa. Composição faz um objeto colaborar com outro, recebido por construtor, sem afirmar que um é uma versão do outro.

Java · trecho de leitura
// Ideia problemática: Pix herda a promessa de parcelar do cartão.
class PagamentoPix extends PagamentoCartao { /* ... */ }

// Colaboração: o caso de uso recebe quem sabe autorizar.
public AutorizarPedido(Autorizador autorizador) {
    this.autorizador = autorizador;
}

Interface declara operações disponíveis. O contrato completo também inclui entradas aceitas, resultados e falhas permitidas. Polimorfismo permite chamar a mesma operação por esse contrato e obter o comportamento da implementação recebida.

Usamos cartão e Pix como simulações. Neste sistema, ambos autorizam, mas só cartão parcela. Em outro produto, as capacidades podem ser diferentes. Composição também tem custo: mais objetos para montar e mais relações para entender.

Single Responsibility Principle · responsabilidade única

S · Uma razão de mudança por responsabilidade [11]

Um recibo reúne dois trabalhos: calcular o preço promocional e escrever o e-mail. A equipe comercial muda a promoção; comunicação muda a saudação. Os motivos são independentes, embora ambos mencionem Pedido.

Coisas que mudam pelo mesmo motivo tendem a ficar juntas. Mudanças de atores distintos pedem uma fronteira clara. “Responsabilidade única” não significa um método por classe.

Recorte didático · versões compiláveis no laboratório
class ResumoPedido {
    BigDecimal total(BigDecimal subtotal) { /* regra comercial */ }
    String email(String cliente) { /* texto de comunicação */ }
}
👀 Refatoração e consequência

Extraia PrecoPromocional e MensagemPedido. Um coordenador pode chamar ambos; ele não precisa escrever o texto nem recalcular a regra. Mudar “Olá” agora alcança a mensagem, sem editar o cálculo.

Open–Closed Principle · aberto para extensão, fechado para modificação

O · Uma variação com um lugar para entrar [12]

Uma campanha oferece 10%; outra desconta R$ 5. O time precisa variar o abatimento sem repetir a conta final, seu arredondamento e suas validações.

Escolha uma fronteira estável para uma variação conhecida. A regra comum usa um contrato; outra implementação acrescenta um comportamento. Algum lugar ainda precisa selecionar e montar essa implementação.

Recorte didático · versões compiláveis no laboratório
interface Desconto {
    BigDecimal abatimento(BigDecimal subtotal);
}
// A calculadora recebe Desconto e faz a parte comum:
return subtotal.subtract(abatimento).setScale(2, RoundingMode.HALF_UP);
👀 Refatoração e consequência

Com subtotal 100, dez por cento produz 90.00; cinco reais produz 95.00. Com subtotal 3, o desconto fixo limita o abatimento a 3 e resulta em 0.00. OCP não exige abstrair cada if: um conjunto pequeno e estável pode continuar explícito.

Troque a campanha, preserve a conta

A escolha da política muda na montagem. A calculadora permanece a mesma. O resultado final é arredondado para duas casas; o Java usa BigDecimal. HALF_UP aproxima para o valor mais próximo e, no empate, afasta do zero: 0.045 vira 0.05. Arredondamos o total final, não cada etapa intermediária.

A única promoção está estável há anos. O agente propõe um registro de plugins. O que revisar?

Liskov Substitution Principle · substituição de Liskov

L · Trocar a implementação sem quebrar a promessa [13]

O cliente recebe PagamentoCartao e chama parcelar(2), permitido de 1 a 12 vezes. PagamentoPix herda cartão, mas lança UnsupportedOperationException para essa chamada.

Uma implementação substituta deve respeitar o contrato esperado pelo cliente: não pode exigir condições mais fortes nem enfraquecer o resultado prometido. O compilador verificar tipos não prova o comportamento.

Recorte didático · versões compiláveis no laboratório
PagamentoCartao pagamento = new PagamentoPix();
pagamento.parcelar(2); // compila; a promessa falha em execução
👀 Refatoração e consequência

Compartilhe apenas autorizar por MeioPagamento; mantenha parcelar no cartão. Uma recusa de negócio prevista no contrato é diferente de não implementar uma operação prometida. Tipos relacionados no mundo real não são automaticamente bons subtipos no código.

Interface Segregation Principle · segregação de interfaces

I · O cliente depende só do que precisa [14]

Consulta precisa de buscar. Recebe um Repositorio que também obriga salvar e exportarTodos. Até o fake de consulta precisa conhecer capacidades que não usa.

Forme contratos pelas necessidades dos clientes. Uma classe concreta pode implementar mais de um contrato. Segregar não exige um serviço, uma classe e uma implantação separados para cada método.

Recorte didático · versões compiláveis no laboratório
interface ConsultaPedidos { String buscar(String id); }
interface GravacaoPedidos { void salvar(String id); }
interface ExportacaoPedidos { List<String> exportarTodos(); }
// Consulta recebe apenas ConsultaPedidos.
👀 Refatoração e consequência

Agora o teste da consulta fornece só buscar; exportação pode evoluir sem ampliar esse contrato. O port Pedidos do Cap 01 tem buscar e salvar usados juntos pelos casos de uso: isso não exige dividi-lo automaticamente.

Dependency Inversion Principle · inversão de dependência

D · Quem escolhe o detalhe externo? [15]

O caso de uso cria new GatewayHttp(). Ao testar uma aprovação, já ficamos presos ao serviço externo. O detalhe técnico passou a decidir como a regra pode ser executada.

A política de alto nível depende de um contrato adequado à sua necessidade. O adapter externo implementa esse contrato. A montagem escolhe o concreto e entrega ao caso de uso.

Recorte didático · versões compiláveis no laboratório
interface Autorizador { boolean autorizar(String id); }
public AutorizarPedido(Autorizador autorizador) {
    this.autorizador = autorizador;
}
👀 Refatoração e consequência

No teste, um fake devolve aprovado ou recusado sem rede. Na aplicação real, config monta o adapter. Injeção pelo construtor é uma técnica; DIP é a direção das dependências. Receber GatewayHttp pelo construtor ainda prende o cliente ao tipo concreto.

O desenho mostra dependências declaradas. Criar o objeto na configuração é necessário, mas não basta: o tipo recebido pelo núcleo também importa.

Uma correção pequena também precisa de prova [17]

👀 Diagnóstico e refatoração-modelo A–E
  1. A · SRP. PrecoPromocional e MensagemPedido isolam motivos distintos. Preserve 100 → 90.00 e o texto esperado. Um teste de saída não prova separação: confira também o diff.
  2. B · OCP. Desconto informa abatimento; Calculadora valida limites, subtrai e arredonda. Percentual de 10%: 37.80 → 34.02. Fixo de 5: 3 → 0.00. A composição escolhe a política.
  3. C · LSP. Cartão e Pix implementam apenas o contrato comum MeioPagamento.autorizar. Parcelar continua específico do cartão. Teste as implementações pelo mesmo tipo.
